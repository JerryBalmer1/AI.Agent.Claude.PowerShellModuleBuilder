# Pass 0036 — Run the blind measurement, and say what it does not measure

## Asked

Run tf-003: build `PSTerraformGraph` from the brief and the four-file seed with
plugin v1.1.0 readable, against the live fixture-2 repositories, without reading
the fixture-2 oracle, the fixture-1 material, the comparator, any prior run
record or any line of the existing PSTerraformGraph implementation, until the
built module is pushed. Then score from fresh built clones, iterate at most
three times, and write the record — including a `## Generalisation comparison`
that states which plugin skills demonstrably shaped phase 1, whether the
ladder's shape-not-correctness claim holds on a second domain, the blindness
bounds that still apply, and a drafted sentence for the README's generalisation
section whatever the numbers say.

## Why

**The oracle's ids were adopted rather than argued with.** All 184 first-shot
differences were four naming conventions, and every one of them was a case where
both readings are defensible. `producer-contract` settles this: the oracle is
right until a decision says otherwise, not until it is inconvenient. No fixture
and no oracle was edited.

**`resolved` was the one worth thinking about rather than just conceding.** The
contract's sentence — *absent means NOT STATED rather than true* — argued for
writing the flag only where false, which is what the producer did and wrote into
its HANDOFF. The oracle states `true` on all twelve resolved `sources` edges.
The rule that reproduces the oracle is sharper than either: resolution is
something the producer *did*, so both outcomes are facts and both are stated,
while `references` and `passes-to` are not resolutions and state nothing. Note
that `hasValidation` and `resolved` are the same shape of question against the
same sentence and resolve **opposite ways**.

**The case scorer was written with the oracle's literal ids**, as fixture 1's
does, rather than normalising ids to be generous. An id is what makes two
producers' graphs mergeable; a scorer that normalised them would be grading
something else. That decision is what makes case 7 a first-shot FAIL, and the
run record says so and states the alternative reading rather than picking the
flattering one silently.

**The generalisation claim was not made.** The numbers would support a strong
sentence. The plugin that produced them contains three `tf-*` skills written
from tf-001 and tf-002 that cite those runs' findings by mechanism and by count
— which is precisely the contamination tf-002 predicted when it recorded that
those skills were deliberately left unwritten. The fixture was unseen; the
mechanism catalogue was not. The drafted README sentence claims what the run
supports — that a plugin carrying a domain's recorded findings stops them
recurring on a fresh fixture in that domain — and names what it would take to
claim more.

## Learned

- **The coverage gate could not fail, and said so on the console.**
  `Invoke-Pester -Configuration` returns nothing without `Run.PassThru`, so
  `$result` was `$null`, the percentage rounded to 0 and the target was `$null`
  — `0 -lt $null` is false. It printed `Line coverage: 0% (target %)` for one
  build. Found by reading the line rather than the exit code, then broken on
  purpose (70 → 99 against 92.48% actual) and seen red. The `PreTag` guard had
  the same defect with the opposite sign. F-5.
- **InvokeBuild's `Write-Build` writes to the output stream.** A function that
  calls it and returns a value returns both. `powershell-module-build`'s
  published `Resolve-BuildDependency` example has exactly this shape, and it is
  harmless only until the return value is used as a path — where it surfaces
  three tasks later as `Cannot find drive '  PSGraphRenderToHtml'`, with the
  resolver's own log line silently missing from the build output. F-6.
- **An oracle scored against itself must come back perfect.** The control run
  failed case 6 — `cases.md` claims the unused variable is *"the only node in
  the fixture with neither"* an incoming nor an outgoing edge, and nine other
  nodes satisfy that literally. The scorer was wrong, not the fixture. Skipping
  the control would have shipped `5 / 7 → 6 / 7`: wrong in the direction of
  modesty, which nobody audits. F-9.
- **A count's multiplier depends on the comparator's internals.** One renamed
  attribute scored 70, because the comparator walks the union of attribute names
  on both sides. One id convention scored 8 across four categories. *Many
  identical differences are one convention* understates it: the inflation factor
  is not visible from the count.
- **Fixture 2 shipped without a case scorer.** `Test-TfFixtureCase.ps1` is
  hard-coded to fixture 1, so the headline number tf-003 exists to produce had
  nothing to compute it from, and this pass wrote a scorer into a plan
  directory where the next run will not find it. F-8.
- **The plugin's two commands did not generalise; its skills did.**
  `/build` and `/test` name `evals/conformance/` and `evals/functional/BRIEF.md`,
  neither of which exists for a `tf` run. The skills they delegate to carried
  over intact.
- **A single-line object separates its entries with commas.** Found by the test
  fixture, not by the measured one — fixture 2 writes `required_providers` only
  in its multi-line block form, so a reader tested only against the thing being
  measured would have shipped it. F-7.

## Capability

The project can now state a blind number for the Terraform domain, and can say
precisely what that number does and does not license: `runs/tf-003-generalisation/`
carries the first score taken against an oracle the building session had not
read, with the contamination that remains named at the level of individual
skills and counts.

`plans/0036-tf-003/Test-Tf003Case.ps1` makes `functional-tf: N / 7` computable
for fixture 2 at all, and `verify.ps1` re-derives every claim in the run record
from a fresh clone, including that the comparator's duplicate-id detection is
live in the scoring path rather than merely present in the file.
